# Phase 6 — Search Architecture (OpenSearch)

> OpenSearch is the **read projection** for catalog browse, layered navigation,
> full-text, autocomplete, and (optionally) vector/AI search. PostgreSQL remains the
> source of truth; the index is rebuildable at any time from the DB.

---

## 1. Why a dedicated engine (not Postgres FTS)

At 5M products with per-store-view pricing/visibility, faceted navigation with live
counts, typo tolerance, synonyms, and relevance tuning, Postgres FTS + GIN can't
compete on latency or features. OpenSearch gives inverted indexes, aggregations
(facets), analyzers, and kNN vectors in one place. Engine-agnostic behind a
`SearchPort` interface so Elasticsearch is a drop-in.

---

## 2. Index topology

**One index per store view** (or one index + a `store_view_id` filter — choose by
catalog size; per-store-view aliasing is cleaner for divergent visibility/pricing):

```
product_index (alias) → product_index_v{N}   (versioned for zero-downtime reindex)
```
- **Alias swap** on full rebuild: build `_v{N+1}`, verify, atomically repoint alias.
- **Document = a denormalized product** (with variant sub-docs / nested variants).

### Document shape (per store view)
```jsonc
{
  "id", "sku", "type", "handle",
  "name", "description",                  // localized for this store view
  "categories": [ids...], "category_paths": ["1.4.9", ...],
  "price": 129.00, "price_range": {min,max}, "on_sale": true,   // resolved price list
  "currency": "USD",
  "attributes": {                          // only searchable/filterable attrs
     "brand": "Acme", "ram_gb": 16, "color": ["red","black"], "display_in": 6.1
  },
  "facets": { "brand": "Acme", "ram_gb": 16, ... },  // keyword/numeric for aggregations
  "in_stock": true, "stock_qty": 42,       // availability projection
  "visibility": "both", "is_visible": true,
  "rating_avg": 4.6, "review_count": 210,
  "created_at", "popularity_score",        // for boosts/sort
  "suggest": { "input": ["iphone", "acme phone"] },  // completion suggester
  "vector": [ ... ]                         // optional embedding (AI search)
}
```
- **Which attributes are indexed** is driven by attribute flags: `is_searchable`,
  `is_filterable`, `used_in_layered_nav`, `is_sortable`. Merchant toggles → mapping +
  reindex.
- Numeric attrs → numeric fields (range facets); select/multiselect → keyword facets
  (option labels + ids); text → analyzed + `keyword` sub-field.

---

## 3. Mapping & analysis

- **Per-language analyzers** (stemming, folding) selected by the store view's language;
  RTL languages handled by their analyzers.
- **Synonyms** and **stop words** managed in admin (`search_synonym`,
  `search_stopword` tables) → compiled into analyzer settings on reindex / synonym API.
- **Custom normalizers** for facets (lowercase, trim) for stable bucketing.
- **Autocomplete:** completion suggester (`suggest` field) + `search_as_you_type` for
  product-name prefix; category & query suggestions too.

---

## 4. Query & relevance

- **Full-text:** `multi_match` (best_fields/cross_fields) over name^weight,
  brand, category, description, with per-field boosts.
- **Boost rules** (`search_boost` table): pin/boost by attribute, category, freshness,
  popularity, margin → `function_score` / `rank_feature`.
- **Facets:** aggregations over facet fields return counts; the UI renders layered
  navigation. Applied filters use `post_filter` so other facet counts stay correct.
- **Sorting:** relevance / price / newest / rating / popularity (sortable attrs).
- **AI / semantic search (ready):** a `vector` dense field + kNN query, hybrid-ranked
  with BM25 (RRF). Embeddings generated by a BullMQ job on product publish; the field
  is optional so classic search works without it.

---

## 5. Indexing pipeline (near-real-time)

```
Domain write (product/price/stock/review) → outbox event → BullMQ "search-index" queue
   → indexer worker:
        - loads the product + resolved per-store-view projection (price, stock, attrs)
        - upserts one doc per store-view index (bulk API, debounced/coalesced)
```
- **Event sources:** `ProductPublished`, `PriceChanged`, `StockMoved` (flip `in_stock`),
  `ReviewApproved` (rating), category/visibility changes.
- **Coalescing:** rapid edits to one product are debounced (e.g. 1–2s) to avoid index
  thrash.
- **Partial updates** for cheap fields (stock/price) via `_update`; full re-project on
  attribute/category change.
- **Full rebuild** job: scan DB → build `_v{N+1}` → alias swap. Used on mapping changes
  or drift recovery.
- **Consistency:** near-real-time (seconds). DB is fallback truth; a nightly reconcile
  job diffs counts and repairs.

---

## 6. Multi-store correctness

- Price/visibility/stock differ per store view → either separate indexes per store view
  (chosen default) or a single index with per-store-view nested pricing + runtime
  filter. Per-store-view indexes keep queries simple and relevance clean at the cost of
  more index storage (acceptable; store views are few).

---

## 7. Trade-offs

- **Denormalization & dual writes** (DB + index) add an eventual-consistency window and
  indexing infra. Justified: it's the only way to hit browse/facet latency at 5M SKU.
  Mitigated by outbox (no lost events) + reconcile job.
- **Per-store-view indexes** multiply storage/rebuild cost; bounded by store-view count.
- **Vector search** adds embedding cost and index size; kept optional/behind a flag.
